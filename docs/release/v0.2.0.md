# match-lang v0.2.0 — Exhaustiveness and Usefulness Checking

**The foundation, and the hard part of the checking side.** v0.2.0 turns the
scaffold into a pattern-match checker that any language can plug into: give
it a match's arms and the scrutinee's type, and it reports the values no arm
handles, each as a concrete witness pattern, the arms no value reaches, and
the redundant alternatives of or-patterns. Sums, products, booleans, bounded
and unbounded integers, characters, opaque literals, arrays, slices,
or-patterns, guards, and empty types are all handled exactly, as verified
against a brute-force reference.

## What is match-lang?

The pattern-matching crate of the `-lang` language-construction family, in
its semantic-analysis tier. Kraken, Iron, Mercury, and the planned functional
language all have `match`; this is the one implementation they share. It
knows nothing about any of them: a language describes its types through the
`Model` trait, so `hir-lang` implements the trait and match-lang depends on
nothing. Decision-tree compilation follows in 0.5.0, over the same model.

## What's new in 0.2.0

### `Model` and `Signature` — the language's side

A model answers two questions about a type: its `Signature` (which
constructors build its values) and the field types of a constructor. Two
optional hooks say which types are empty and name variants for printing.

```rust
use match_lang::{check, Arm, Model, Pat, Signature};

/// `Option<bool>`: 0 is the option, 1 the bool inside it.
struct Lang;

impl Model for Lang {
    type Ty = u8;

    fn signature(&self, ty: &u8) -> Signature<u8> {
        if *ty == 0 { Signature::Sum { count: 2 } } else { Signature::Bool }
    }

    fn fields(&self, _: &u8, variant: u32, out: &mut Vec<u8>) {
        if variant == 1 {
            out.push(1);
        }
    }

    fn variant_name(&self, _: &u8, variant: u32) -> Option<&str> {
        Some(if variant == 0 { "None" } else { "Some" })
    }
}

let arms = [
    Arm::new(Pat::variant(1, [Pat::bool(true)])),
    Arm::new(Pat::variant(0, [])),
    Arm::new(Pat::variant(1, [Pat::bool(true)])),
];
let report = check(&Lang, &0, &arms)?;
assert_eq!(report.missing()[0].display(&Lang).to_string(), "Some(false)");
assert_eq!(report.unreachable(), &[2]);
# Ok::<(), match_lang::Error>(())
```

Signatures cover sums (`Sum { count }`, with `count` 0 for empty types),
products (tuples, structs, records, boxes, references), `Bool`, bounded
integers (`Int { min, max }` over `i128`), `Char`, unbounded integers
(`BigInt`), opaque literals compared by equality (`Opaque`: strings, floats,
symbols), fixed-length arrays, and variable-length slices.

### `Pat` and `Arm` — the patterns

Patterns are built bottom-up: `wild`, `variant`, `product`, `bool`, `int`,
`range`, `char`, `char_range`, `lit`, `or`, `slice`, and `slice_rest`. A
pattern that does not fit its type is reported as `Error::InvalidPattern`
with the arm, the node's preorder index, and a `Reason`, before any analysis.
`Drop`, `Clone`, and `Display` of patterns are iterative, so a pattern nested
100,000 deep is as safe as a flat one.

### `check`, `Checker`, and `Report` — the result

`check` is the one-call entry point. `Checker` adds a configurable step limit
and witness limit and reuses its buffers from one check to the next, so a
compiler checking every match in a program allocates almost nothing after
the first few. A `Report` gives:

- `is_exhaustive` and `missing`: at least one `Witness` when the match is not
  exhaustive, each a tree of `Ctor` nodes with their types, matching at least
  one value and no value any unguarded arm matches;
- `unreachable`: the arms no value reaches;
- `redundant`: the or-pattern alternatives no value reaches, by arm and
  preorder node index, outermost first;
- `steps`: the work the check used.

### The algorithm

Maranget's usefulness algorithm ("Warnings for pattern matching", JFP 2007)
with constructor splitting, as modern compilers run it: one pass computes the
usefulness of every row; each column is split into the constructors its
patterns mention plus a single "missing" constructor for all the rest;
witnesses are built on the way back.

- **Ranges.** Integer and character domains are cut into disjoint segments
  in one sorted sweep. Characters are analysed over a gap-free index space,
  so a range across the surrogate block covers both sides and every witness
  is a valid scalar value.
- **Slices.** Lengths are grouped into intervals cut at each length a pattern
  singles out. A run of lengths where the rest patterns' prefixes and
  suffixes no longer overlap is one constructor, so a 20,000-element pattern
  beside `[..]` costs its length, not its length squared.
- **Or-patterns** are expanded in place in left-to-right preorder; each
  alternative's usefulness is tracked, and alternatives that are themselves
  or-patterns are resolved from their own.
- **Guards** are treated as possibly failing, and re-tried for each
  alternative that matches.
- **Empty types.** A constructor with an empty field has no values: it is
  never required, and arms only it could reach are unreachable.
- **Relevancy.** Under a constructor examined only for usefulness (because
  another one is missing), rows with a wildcard head are not explored, and
  rows after the last relevant one are dropped. This is what keeps ordinary
  matrices polynomial: a 1,000-by-1,000 matrix testing one column per row
  takes 7 million steps instead of 2^1000 paths.

### Safety on hostile input

- No recursion anywhere input reaches: the specialization recursion runs on
  an explicit stack of frames.
- Rows are persistent stacks sharing their tails, so specializing pushes only
  the head constructor's fields: a 100,000-field tuple is linear, not
  quadratic.
- Every unit of work is charged to a step budget (2^24 by default). Deciding
  exhaustiveness is NP-hard in general; a match that needs more is an
  `Error::StepLimit`, never a hang.
- A model that contradicts itself is an `Error::Model`, never a panic.

### Examples

Two runnable programs: `option` (the one-call path) and `language` (a small
language's checker with named enums and structs, integers, interned strings,
slices, guards, and or-patterns, printing compiler-style messages and mapping
preorder node indices back to the language's own pattern tree).

### Dependency wiring

No first-party dependency is wired. The crate is generic over the language's
types, so `hir-lang` implements `Model` rather than match-lang depending on
it; `intern-lang` symbols fit `Pat::lit` ids directly; `diag-lang` is not
wired because turning a report into diagnostics needs the language's spans.
The decisions are recorded in `dev/ROADMAP.md`.

### Ahead of the roadmap

Slices (planned for 0.5.0) and budgets with adversarial matrices (planned for
0.9.0) are delivered here; the roadmap records the moves.

## Verification

Run on Windows x86_64, on Rust stable and on the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
cargo build --examples
```

All green. Counts at this tag, identical with all and with no default
features: 8 unit, 52 integration, and 6 property tests, plus 84 doctests
(including every `rust` example in `README.md` and `docs/API.md`). The
property tests compare exhaustiveness, every witness, every unreachable arm,
and every redundant alternative with a brute-force reference over random
types and matches; a one-off run of 200,000 cases per property found no
disagreement, and each of the engine bugs planted to test the tests (in
guards, range boundaries, slice splitting, empty variants, alternative
marking, and relevancy) was caught. Linux and macOS are covered by the CI
matrix.

Benchmarks (`cargo bench --bench bench`, release profile, Windows x86_64):

| Benchmark | Time |
|---|---:|
| 100,000 arms over a 100,000-variant enum | ~7.9 ms |
| 100,000 integer literals and a wildcard | ~10.9 ms |
| 100,000 adjacent ranges covering `i64` | ~9.4 ms |
| 16-column truth table (65,536 arms) | ~77 ms |
| 1,000 by 1,000, one test per row | ~55 ms |
| 10,000 small matches through one `Checker` | ~4.1 ms |
